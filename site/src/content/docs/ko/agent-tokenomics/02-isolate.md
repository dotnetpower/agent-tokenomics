**목표:** "비용이 많이 든다"는 막연한 상태를 검증 가능한 하나의 구체적인 원인으로 좁힙니다.

## 원인 범주

| 범주 | 진단에서 나타나는 신호 | 분리 실험 |
|------|------------------------|-----------|
| **저장소 사실 재학습** | 많은 세션의 시작 부분에서 같은 탐색 호출과 같은 수정된 명령이 반복됨 | 세션 간에 동일한 초기 도구 호출 수를 셉니다 |
| **사용하지 않는 도구** | 한 번도 호출되지 않는데 요청마다 전송되는 도구 정의 | 사용하지 않는 도구별로 `definition tokens × requests`를 계산합니다 |
| **실패 루프** | 한 턴에서 같은 오류 시그니처가 반복됨 | 턴당 반복 횟수를 세고 대화 기록을 읽습니다 |
| **비대한 도구 출력** | 몇 개의 도구가 도구 출력 토큰의 대부분을 차지함 | 출력 토큰 기준으로 도구 순위를 매기고 가장 큰 결과를 살펴봅니다 |
| **기록 증가** | 새 정보는 적은데 입력이 가파르게 증가하고, 도구 결과가 아닌 대화 텍스트가 더 큰 비중을 차지함 | 기록을 잘라내거나 요약한 상태로 세션을 재생하고, 캐시 적중률이 급락하지 않는지 확인합니다 |
| **접두부 변동(캐시 미스)** | 낮은 캐시 적중률 | 연속된 요청을 비교(diff)해 처음으로 달라지는 지점을 찾습니다 |
| **과도하게 큰 모델 / 강도** | 쉬운 단계에서도 가장 큰 모델을 사용함 | 해당 단계를 더 작은 모델로 다시 실행합니다 |
| **재시도와 재작업** | 승인된 변경 하나당 도구 호출이 많음 | 되돌리거나 다시 작업하며 끝난 턴을 확인합니다 |
| **컨텍스트 열화** | 컨텍스트 윈도우가 차기 전에 긴 세션에서 품질이 떨어지고, 앞부분에 준 지침이 무시됨 | 짧은 요약을 담은 새 세션에서 작업을 다시 실행하고 성공 여부를 비교합니다 |
| **도구 수 × 단계 수 승수** | 도구 카탈로그가 크고 *동시에* 작업당 단계 수도 많음 | `schema tokens × steps`를 계산하고, 최소한의 도구 집합으로 다시 실행합니다 |
| **큰 정적 문서 × 호출 횟수** | 하나의 참조 문서(규칙, 치트 시트, 정책)가 단계의 고정 토큰 중 큰 비중을 차지하며, 그 단계가 두 번 이상 호출됨 | 구성 요소를 `tokens × calls` 기준으로 정렬하고, 관련 있을 때만 문서를 첨부해 다시 실행한 뒤 비교합니다 |
| **중복된 파이프라인 단계(팬아웃)** | 사용자 요청 하나에 LLM 호출이 많고, 일부는 작은 점검 또는 분류기임 | 요청 하나를 끝까지 추적하고, 각 단계를 건너뛰거나 합치거나 규칙으로 대체하면 무엇이 달라지는지 따져 봅니다 |
| **세션별 무제한 상태** | 내부 메시지, 보고서, 도구 결과가 잘리지 않아 턴이 지날수록 입력이 증가함 | 코드에서 잘라내기나 윈도 처리 로직을 찾고, 상태에 상한을 둔 채 긴 세션을 재생합니다 |
| **짧아서 캐시할 수 없는 프롬프트** | 여러 단계의 고정 프롬프트가 공급자의 최소 캐시 가능 길이보다 짧음 | 각 단계의 고정 토큰을 최소 길이와 비교하고, 해당 단계의 `cached_tokens`가 0인지 확인합니다 |
| **지나치게 넓은 프롬프트 / 지침** | 에이전트가 넓게 탐색하거나, 지침이 코드에 이미 있는 내용을 반복함 | 범위를 좁힌 프롬프트와 다듬은 지침 파일로 바꾸고, 단계 수와 성공 여부를 비교합니다 |

## 방법

1. 그럴듯해 보이는지가 아니라 (기준선에서 구한) **걸려 있는 추정 토큰 수**를 기준으로 범주의 순위를 매깁니다.
2. 순위가 가장 높은 범주에 대해 **그 변수만** 바꾸는 실험을 설계합니다(예: 사용하지 않는 도구만 제거하고
   다른 것은 바꾸지 않습니다).
3. 가설을 숫자를 넣어 한 문장으로 작성합니다.
   *"사용하지 않는 도구 정의가 요청 7건에 걸쳐 약 14,000 토큰(입력의 19%)을 차지합니다."*

## 해석

- 기록을 원인으로 지목하기 전에 **도구 출력**부터 배제합니다. 증가분의 대부분이 도구 결과라면,
  대화를 요약하는 것보다 도구 결과를 잘라내거나 페이지로 나누는 편이 더 저렴하고 안전합니다.
- 두 원인이 겹치면(예: 실패 루프가 기록도 부풀리는 경우) 토큰을 **근본 원인**(루프)에 귀속하고
  그것부터 처리합니다.
- 어떤 범주도 전체 토큰의 약 10%를 넘게 설명하지 못한다면 기준선이 양호한 것일 수 있습니다.
  더 최적화하기 전에 *작업* 자체가 그만큼의 컨텍스트를 정말로 필요로 하는지 확인합니다.

## 추가 자료(논문)

학회 등급 순, 같은 등급 안에서는 인용 수 순으로 정렬했습니다. 각 결과는 자신의 워크로드에서 검증해야 할 가설로 취급합니다. 전체 목록은 [논문](../../papers/)을 참고하세요.

- [SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering](https://arxiv.org/abs/2405.15793) — NeurIPS 2024, 인용 2,357회. 간결하고 제한된 관찰을 포함한 인터페이스 설계가 에이전트의 성공률을 좌우함을 보여 줍니다.
- [Reducing Cost of LLM Agents with Trajectory Reduction](https://arxiv.org/abs/2509.23586) — PACMSE 2025, 인용 68회. 궤적에서 낭비를 덜어 내 에이전트 비용을 줄입니다.
- [Agentless: Demystifying LLM-based Software Engineering Agents](https://arxiv.org/abs/2407.01489) — 프리프린트 2024, 인용 566회. 위치 파악-수정-검증으로 고정된 파이프라인이 SWE-bench Lite에서 개방형 에이전트 루프에 견줄 만한 성능을 낮은 비용으로 달성합니다.
- [The Complexity Trap: Simple Observation Masking Is as Efficient as LLM Summarization for Agent Context Management](https://arxiv.org/abs/2508.21433) — 프리프린트 2025, 인용 66회. 에이전트 컨텍스트 관리에서 단순한 관찰 마스킹이 LLM 요약만큼 효율적입니다.
- [Efficient Agents: Building Effective Agents While Reducing Cost](https://arxiv.org/abs/2508.02694) — 프리프린트 2025, 인용 40회. 에이전트 시스템 설계에서 효율과 효과 사이의 절충 관계를 체계적으로 연구합니다.
