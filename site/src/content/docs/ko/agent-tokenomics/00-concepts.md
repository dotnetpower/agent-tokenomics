## 1. 모델 호출은 무상태입니다

모델은 호출 사이에 아무것도 기억하지 않습니다. 에이전트가 "기억"하는 것처럼 보이는 이유는 **매 요청마다**
지침, 도구 정의, 지금까지의 대화를 **다시 전송**하기 때문입니다. 따라서 토큰 비용은 사용자가 입력하는 내용보다
프레임워크가 호출마다 **함께 실어 보내는 내용**에 더 크게 좌우됩니다.

## 2. 요청 하나의 구조

| 구성 요소 | 방향 | 요청마다 바뀌는가? | 흔한 낭비 |
|-----------|------|--------------------|-----------|
| 시스템 프롬프트(프레임워크 + 사용자 작성) | 입력 | 아니요 — 고정 | 길고 반복되는 규칙 |
| 지침 파일 / 상시 사실 | 입력 | 드물게 | 코드에서 이미 알 수 있는 사실, 중복 |
| **도구 정의**(스키마) | 입력 | 드물게 | 한 번도 호출하지 않는 도구 |
| 대화 기록(사용자, 어시스턴트) | 입력 | 턴마다 증가 | 지난 주제, 이미 해결된 우회 작업 |
| **도구 결과**(파일 읽기, 명령 출력) | 입력 | 단계마다 증가 | 파일 전체, 장황한 로그 |
| 첨부 파일 / 검색된 컨텍스트 | 입력 | 작업마다 | 관련 없거나 중복된 컨텍스트 |
| 현재 사용자 프롬프트 | 입력 | 예 | 보통 가장 작은 부분 |
| 모델 텍스트, 도구 호출 | 출력 | 예 | 장황한 답변, 질문 되풀이 |
| 추론("thinking") | 출력(보통 출력으로 과금) | 예 | 작업에 필요한 수준을 넘는 추론 강도 |

위쪽 행은 호출마다 그대로인 **접두부**를 이룹니다. 접두부는 캐싱에서 중요합니다(5절 참조).

## 3. 에이전트 루프는 모든 것을 곱절로 늘립니다

```text
step 1: model call ─► tool call ─► result appended
step 2: model call (re-sends prefix + history + result 1) ─► tool call ─► result appended
step 3: model call (re-sends prefix + history + result 1..2) ─► …
```

각 단계는 과금되는 모델 호출이고, 호출할 때마다 이전 내용을 모두 다시 전송합니다. *n*단계로 이루어진 작업의 입력 토큰은 다음과 같습니다.

```text
input tokens ≈ n × prefix + Σ(history and tool results accumulated before each step)
```

첫 번째 항은 단계 수에 비례해 늘어납니다. 두 번째 항은 단계마다 쌓인 내용을 이후의 모든 단계가 다시 전송하므로
선형보다 빠르게 늘어납니다. 그래서 **단계 수 감소**, **결과 크기 감소**, **접두부 크기 감소**가 모두 효과를 내고,
루프에 갇히면 비용이 크게 늘어납니다.

**파이프라인도 비용을 곱절로 늘립니다.** 모든 에이전트가 자유로운 루프로 동작하는 것은 아닙니다. 프로덕션 에이전트
중에는 사용자 요청 하나에 고정된 모델 호출 체인을 실행하는 경우가 많습니다(예: 안전성 검사 → 쿼리 재작성 → 라우터 →
분류기 → 답변 → 후속 질문 → 최종 응답). 사용자에게는 질문 하나로 보이지만, 제공자는 **단계마다 호출 한 건**을
과금하고, 각 단계는 자체 시스템 프롬프트와 참조 문서를 함께 보냅니다. 이를 **팬아웃**(사용자 요청당 LLM 호출 수)이라고
합니다. 여러 단계에 첨부되었거나 두 번 호출되는 단계에 첨부된 큰 내용은 `tokens × calls`만큼 비용이 듭니다.

## 4. 무엇에 대해 과금되는가

| 항목 | 설명 | 중요한 이유 |
|------|------|-------------|
| 캐시되지 않은 입력 토큰 | 처음부터 처리한 입력 | 입력 정가 적용 |
| **캐시된 입력 토큰** | 제공자의 프롬프트 캐시에서 처리한 입력 | 대부분의 제공자가 할인된 요율로 과금 |
| 출력 토큰(추론 포함) | 모델이 생성한 모든 내용 | 보통 입력보다 토큰당 단가가 높음 |

요율은 제공자와 모델에 따라 다르고 수시로 바뀝니다. 기사에 나온 비율에 의존하지 말고, 사용하는 모델의 최신 가격표를
확인하세요. 요청 하나의 총비용은 `uncached_in × p_in + cached_in × p_cached + out × p_out`이며, 이를 모든
요청에 대해 합산합니다.

**비용만이 목표는 아닙니다.** 무엇을 최적화하는지에 따라 지표가 달라지므로 먼저 정하세요.

| 목표 | 일반적인 상황 | 지표 |
|------|---------------|------|
| 비용 | 종량제 또는 크레딧 | 작업당 유형별 토큰, 성공 작업당 비용 |
| 처리 용량 | 예약 / 프로비저닝 처리량, 속도 제한 | 요청당 분당 토큰, 사용률, 동시 처리 사용자 수 |
| 지연 시간 | 대화형 사용 | 호출당 입력 토큰, 첫 토큰 시간, p95 종단 간 시간 |

입력 토큰이 줄어들면 대체로 세 가지 목표 모두에 도움이 됩니다. 캐싱은 사용하는 배포 유형에서 제공자가 캐시된 토큰을
유리하게 계산할 때만 비용과 처리 용량을 개선합니다(5절의 점검 목록 참조).

## 5. 프롬프트 캐싱

제공자는 최근에 처리한 요청과 **가장 길게 일치하는 접두부**를 재사용할 수 있습니다. 캐시 적중은 요청의 앞부분이
*완전히 동일*해야 가능하므로, 앞쪽에서 하나라도 바뀌면(지침 순서 변경, 도구 목록 수정, 기록 재작성) 그 지점부터는
캐시가 무효화됩니다. 동작은 제공자, 모델, 배포 유형마다 다릅니다. 모델을 바꾸면 이전 캐시를 재사용하지 못합니다.
설계 원칙은 **고정된 내용을 앞에, 변하는 내용을 뒤에, 기록은 추가만** 하는 것입니다. VS Code에서는
[Cache Explorer](https://code.visualstudio.com/docs/agents/agent-troubleshooting/cache-explorer)로 연속된 요청이
처음 달라지는 지점을 확인할 수 있습니다. 제공자 문서는 다음과 같습니다.
[Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching),
[OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching)

### 제공자 캐싱: 확인할 사항

캐싱 규칙은 제공자, 모델 계열, 배포 유형에 따라 다르며 계속 바뀝니다. 캐싱을 전제로 설계하기 전에 다음 질문의
답을 문서로 확인하세요. 오른쪽 열에는 Azure OpenAI와 OpenAI의 공식 문서 내용을 2026-11-03 기준으로
정리했습니다. 사용하는 모델에 대해서는 다시 확인하세요.

| 질문 | 중요한 이유 | 문서 내용(2026-11-03 기준) |
|------|-------------|----------------------------|
| 캐시할 수 있는 최소 접두부 길이는? | 짧은 프롬프트(가드레일, 소형 분류기, 요약기)는 캐시되지 않을 수 있음 | Azure OpenAI: 요청이 1,024토큰 이상이어야 하며 처음 1,024토큰이 동일해야 합니다. OpenAI: GPT-5.6 이상은 최소 1,024토큰이며, 이전 모델은 다릅니다 |
| 어떤 모델과 보존 정책을 지원하는가? | 지원하지 않는 모델이거나 확장 보존을 쓸 수 없으면 계획이 달라짐 | Azure: GPT-4o 이상에서 인메모리 보존을 지원합니다. 확장 보존은 나열된 일부 모델에서만 지원하므로 "mini" 변형을 포함해 정확한 모델을 목록에서 확인해야 합니다 |
| 적중 여부는 어디에서 확인하는가? | 볼 수 없는 것은 조정할 수 없음 | Azure chat completions: `usage.prompt_tokens_details.cached_tokens`(0이면 미적중). GPT-5.6 이상 Standard 배포에서는 `cache_write_tokens`도 제공합니다 |
| 캐시 키가 도움이 되는가? | 관련 요청을 한곳으로 라우팅하면 적중률이 높아짐 | Azure(GPT-5.6 이상): 공유 접두부마다 `prompt_cache_key` 하나를 재사용합니다. 하나의 접두부와 키 조합에서 분당 약 15개 요청을 넘으면 일부 요청이 미적중할 수 있으므로, 안정적인 매핑으로 여러 키에 분산합니다 |
| 얼마 동안 보관되는가? | 사용하지 않는 시간이 길 때 캐시가 낭비되는지 결정 | Azure 인메모리: 보통 5–10분 동안 사용하지 않으면 삭제되며, 최대 1시간 안에는 항상 삭제됩니다. 확장 보존: 최대 24시간(키/값 텐서를 GPU 로컬 저장소로 오프로드). GPT-5.6 이상에서는 정책 필드가 사용 중단되고 최소 30분의 수명이 적용됩니다 |
| 과금과 집계는 어떻게 되는가? | 캐싱이 비용, 처리 용량, 또는 둘 다 절감하는지 결정 | Azure: Standard에서는 캐시 읽기에 할인이 적용되고, Provisioned 배포에서는 입력을 최대 100% 할인합니다. GPT-5.6 이상에서는 캐시 쓰기에 요금이 부과될 수 있습니다. OpenAI: 가격은 모델마다 다릅니다. 캐시된 토큰이 처리 용량 사용률에 어떻게 반영되는지 확인하세요 |
| 무엇이 어디에 저장되는가? | 보안 및 데이터 상주 검토 | OpenAI: 캐시에는 토큰이 아니라 키-값 텐서가 저장됩니다. Azure: 구독 간에 공유되지 않으며, 확장 보존은 배포 유형의 리전 또는 데이터 영역 경계 안에 유지됩니다 |
| 비활성화하거나 삭제할 수 있는가? | 일부 규정 준수 사례에 필요 | Azure: GPT-5.6 이상 Standard 배포에서는 중단점 없이 `explicit` 모드를 사용하면 캐싱이 비활성화됩니다. 이전 모델과 관리형 프로비저닝 배포에서는 비활성화할 수 없습니다 |

캐시할 수 없을 만큼 짧은 프롬프트는 설계를 점검하라는 신호입니다. 억지로 길이를 채우지 마세요. 해당 단계를
인접한 단계와 합치거나, 결정적(deterministic) 검사로 옮기거나, 작은 비용으로 받아들이세요. 임계값을 맞추려고
의미 없는 토큰을 추가해서는 안 됩니다.

## 6. 컨텍스트 윈도우와 컨텍스트 열화

**컨텍스트 윈도우**는 모델이 한 요청에서 고려할 수 있는 최대 범위입니다(입력과 출력이 함께 사용). 이는 엄격한
한계이면서 느슨한 한계이기도 합니다. 모델은 긴 컨텍스트의 중간에 있는 정보를 앞이나 끝에 있는 정보보다 덜 안정적으로
사용하므로([Lost in the Middle](https://arxiv.org/abs/2307.03172)), 윈도우가 가득 차기 훨씬 전부터 품질이
떨어질 수 있습니다. 비용과 품질 모두 **작업에 필요한 만큼, 그러나 충분한** 컨텍스트만 사용하라고 말합니다.

## 7. 도구에는 두 가지 비용이 있습니다

1. **정의 비용** — 활성화한 모든 도구의 스키마는 사용 여부와 관계없이 매 요청의 접두부에 포함됩니다.
2. **결과 비용** — 도구가 반환한 내용은 기록에 추가되어 이후 모든 단계에서 다시 전송됩니다.

사용하지 않는 도구를 가지치기하면 첫 번째 비용을 줄일 수 있고, 결과를 자르거나 페이지로 나누거나 요약하면 두 번째
비용을 줄일 수 있습니다.

## 8. 품질이 없는 비용 절감은 의미가 없습니다

실패하는 저렴한 실행은 절감이 아닙니다. **성공 작업당 비용**을 추적하세요. 또한 단계별 오류는 긴 루프에서 누적되므로
([입증](../03-prove/#multi-step-reliability)의 표 참조), 루프를 줄이면 성공률과 비용을 함께 개선할 수 있습니다.

| 도구 정의 비용 | 사용하지 않는 도구 | [원인 분리](../02-isolate/) |

| 루프에 의한 비용 증폭 | 실패 루프, 재시도 | [입증](../03-prove/) |
| 기록 누적 | 기록 증가, 컨텍스트 열화 | [개선: 컨텍스트 압축](../04-improve/#compaction-without-losing-the-cache) |

## 적용 예시

합성 로그 [`sample-requests.jsonl`](https://github.com/dotnetpower/agent-tokenomics/blob/main/examples/sample-requests.jsonl)에서
세션 `s1`의 첫 요청은 입력 토큰이 9,200개입니다. 도구 정의 네 개를 합치면
220 + 180 + 900 + 1,100 = **2,400토큰(해당 요청의 약 26%)**이고, 그중 두 도구는 한 번도 호출되지 않습니다.
요청 2부터는 입력 토큰 9,600개 중 9,000개를 캐시에서 처리합니다. *접두부가 동일하게 유지되었기 때문*입니다.
세션 도중에 도구를 제거하거나 지침 순서를 바꾸면 이 적중률은 떨어집니다. 로그 하나만으로도 접두부 오버헤드,
도구 정의 비용, 캐싱이라는 세 가지 개념을 확인할 수 있습니다.

## 추가 자료(논문)

학회 등급, 인용 수 순으로 정렬했습니다. 논문의 결과는 가설로 보고 자신의 워크로드에서 검증하세요. 전체 목록은 [논문](../../papers/)에서 볼 수 있습니다.

- [ReAct: Synergizing Reasoning and Acting in Language Models](https://arxiv.org/abs/2210.03629) — ICLR 2022, 인용 13,383회. 추론과 도구 동작을 교차하는 방식으로, 이 가이드가 비용을 분석하는 에이전트 루프에 해당합니다.
- [Efficient Memory Management for Large Language Model Serving with PagedAttention](https://arxiv.org/abs/2309.06180) — SOSP 2023, 인용 9,724회. PagedAttention으로 KV 캐시 메모리를 관리해 서빙 처리량을 높이며, vLLM의 기반입니다.
- [Lost in the Middle: How Language Models Use Long Contexts](https://arxiv.org/abs/2307.03172) — TACL 2023, 인용 5,818회. 관련 정보가 긴 입력의 중간에 있으면 정확도가 떨어집니다.
- [SGLang: Efficient Execution of Structured Language Model Programs](https://arxiv.org/abs/2312.07104) — NeurIPS 2023, 인용 1,783회. RadixAttention으로 접두부를 공유하는 호출 간에 KV 캐시를 재사용하며, 접두부 캐싱의 토대입니다.
- [RULER: What's the Real Context Size of Your Long-Context Language Models?](https://arxiv.org/abs/2404.06654) — 프리프린트 2024, 인용 1,580회. 실제로 유효한 컨텍스트 길이가 공시된 윈도우보다 짧은 경우가 많음을 보여 주는 벤치마크입니다.
