Track B는 LLM 에이전트를 **직접 만들거나 운영하는** 엔지니어를 위한 **에이전트 토큰 이코노믹스(Agent Tokenomics · Token Economics)** 가이드입니다. 토큰 비용이 높은 상황을
운영 장애처럼 다룹니다. 추측에 의존하지 말고 절차에 따라 원인을 확인하세요.

처음이라면 에이전트가 토큰을 쓰는 방식을 설명하는 [0. 개념](00-concepts/)부터 읽은 다음 절차를 따라가세요.

```text
Diagnose → Isolate → Prove → Improve → Result
   └────────── repeat with the next biggest cause ──────────┘
```

| 단계 | 질문 | 산출물 |
|------|------|--------|
| [0. 개념](00-concepts/) | 에이전트는 토큰을 어떻게 쓰는가? | 공통 개념 |
| [1. 진단](01-diagnose/) | 지금 토큰이 어디에 쓰이는가? | 측정된 기준선 |
| [2. 원인 분리](02-isolate/) | 어떤 원인 때문에 비용이 드는가? | 우선순위를 매긴 가설 하나 |
| [3. 입증](03-prove/) | 그 원인이 실제로 존재하며 규모는 얼마인가? | 재현하고 수치화한 낭비 |
| [4. 개선](04-improve/) | 원인에 맞는 어떤 변경으로 낭비를 줄일 수 있는가? | 변경 하나, 실험 하나 |
| [5. 결과](05-result/) | 품질 저하 없이 비용이 줄었는가? | 유지 / 되돌리기 결정 |
| [6. 골든 데이터셋과 루브릭 평가](06-golden-dataset-and-rubric/) | 단일·멀티턴 정답(키워드·의도)과 품질을 어떻게 채점하는가? | 엑셀(CSV) 평가셋 및 하이브리드 루브릭 |

측정·최적화·평가·배포를 논의할 때는 최소 자료로 확인하는 [하단의 실무 체크리스트](#practical-checklist)를 활용합니다.

실행 가능한 [측정 스크립트](https://github.com/dotnetpower/agent-tokenomics/tree/main/examples)도 제공합니다.

## 준비물

- **요청 로그**: 모델 호출마다 한 건씩 기록한 로그입니다. 입력 / 캐시된 입력 / 출력 토큰, 전송한 도구 정의,
  도구 호출과 오류, 해당 호출이 속한 사용자 프롬프트(턴)와 세션을 포함합니다. 대부분의 에이전트 프레임워크가
  이 로그를 내보낼 수 있습니다. 그렇지 않다면 모델 클라이언트를 감싸서 직접 기록하세요.
- 다시 실행할 수 있는 **작업 세트**(대표 작업 5–20개)와 자동 성공 판정 기준
- 한 번에 변수 하나만 바꾸는 원칙

<a id="제0-원칙"></a>
## 기본 원칙

토큰을 줄이는 것은 **작업 성공률이 떨어지지 않을 때만** 성과입니다. 항상 비용과 품질 지표를 함께 보고하세요.

<a id="practical-checklist"></a>
## 실무 체크리스트

> **기준일: 2026-11-19.** 이 체크리스트는 저장소의 공개 절차와 연결된 과금 가이드만을 바탕으로 독립적으로 작성한 일반적인 **합성 체크리스트**입니다. 실제 고객 사례나 실측 자료가 아니며 절감을 보장하지 않습니다. 제공자 정책, 요율, 지원 설정, 관측 필드는 바뀔 수 있으므로 운영을 결정하기 전에 해당 원문을 다시 확인해야 합니다.

- 작업 범위, 성공 기준, 자료 공유 범위를 먼저 합의합니다. 열린 질문으로 설명을 듣고 필요한 후속 질문만 선택합니다. 특정 제품, Copilot 설정, 관측 플랫폼을 필수 요건으로 삼지 않습니다.
- **관측됨**, **적용 안 됨**(해당 업무 범위 밖), **미확인**(증거 부족), **미지원**(현재 시스템이 설정이나 필드를 제공하지 않음)을 구분하고 이유를 남깁니다. 어느 상태도 사용량 0이나 낮은 성숙도를 자동으로 뜻하지 않습니다.
- 마지막 열은 확인을 시작하기 위한 최소 자료의 예시이지 제출 목록이 아닙니다. 전체 운영 로그보다 기존 집계, 민감정보를 제거한 짧은 발췌, 화면 설명을 우선합니다. 원문 수집을 최소화하고 공유 전 개인정보, 자격 증명, 내부 명칭, 원래 식별자를 제거합니다. 관계를 유지할 때는 로컬 가명 ID를 사용하고 접근 권한과 보존 기간을 합의하며, 비공개 증거나 링크를 공개하지 않습니다.
- 합의한 기준, 관측된 증거, 가설을 구분합니다. 증거로 확인한 공백 하나와 되돌릴 수 있는 변경 하나를 선택하고 품질 가드레일과 유지·되돌리기 조건을 실험 전에 정합니다. 증거가 부족하면 배포를 승인하기보다 먼저 측정합니다.

| 주제 | 중립적인 열린 질문 | 확인 포인트 | 쉬운 설명 | 최소 확인 자료 |
|---|---|---|---|---|
| 1. 재시도와 실패 루프 | 같은 오류가 반복되면 어떤 과정을 거쳐 재시도, 방향 전환, 중단을 결정합니까? | 동일 오류의 식별 기준, 모델 호출·단계·재시도 상한과 요청/세션별 적용 범위, 중단·담당자 전달 동작을 확인합니다. 백오프 대기와 재시도 횟수 제한을 구분합니다. | 다음 시도까지 오래 기다린다고 전체 시도 횟수가 제한되지는 않습니다. | 중단 이유가 포함된 실패 흐름 하나와 해당 제한 설정의 짧은 발췌입니다. 민감정보는 제거합니다. |
| 2. 단일·멀티 에이전트 | 같은 업무를 끝까지 수행할 때 단일·멀티 에이전트의 결과는 어떻게 다르며, 그 차이를 어떻게 설명합니까? | 전체 호출 수와 부모·자식 입력/출력, 조율·검토·재작업, 전체 소요 시간과 성공률을 비교합니다. 각 호출은 한 번만 합산하며, 자식 호출이 이미 포함된 부모 집계에 다시 더하지 않습니다. | 병렬로 빨리 끝내는 것과 토큰을 적게 쓰는 것은 다릅니다. | 같은 작업의 비교 자료 하나입니다. 호출별 합계 또는 포함 범위가 명시된 집계면 됩니다. |
| 3. 프롬프트 측정과 버전 | 요청의 각 구성 요소를 어떻게 조합하고 측정하며 버전으로 관리합니까? 기록 증가, 접두부 변경, 도구 지연 로딩은 어떻게 확인합니까? | 지침, 사용자 입력, 대화 기록, 검색, 도구 정의·결과, 응답 스키마를 고정/동적으로 나누고 변경 이력을 평가에 연결합니다. 정적 추정에는 토크나이저/모델 버전을 표시하고 실제 provider usage와 구분하며 토크나이저 차이를 기록합니다. 활성화된 도구가 모두 즉시 전송된다고 가정하지 말고 실제 스키마, 캐시 적용 조건, 접두부 안정성, 보고된 재사용을 확인합니다. | 프롬프트 파일이 짧아도 전체 요청이 짧다는 뜻은 아니며, 추정치는 사용량 명세가 아닙니다. | 측정 방법이 표시된 구성별 토큰 지도 하나와 프롬프트 버전에 연결된 평가 기록입니다. |
| 4. 검색 증강 생성(RAG) | 검색한 자료를 최종 모델 입력으로 어떻게 고르며, 줄일 때 반드시 남겨야 할 것은 무엇입니까? | 조각 수·길이·겹침·중복·재순위화·최종 전달 토큰을 확인합니다. 필수 근거, 접근 권한, 출처를 보존하고 입력 크기뿐 아니라 검색 품질도 확인합니다. | 인덱스가 작아졌다고 모델 입력도 줄었다고 볼 수는 없습니다. | 선택한 조각, 최종 토큰 수, 근거·권한 확인이 드러나는 익명화된 검색 요약 하나입니다. |
| 5. 모델과 추론 강도 | 모델이나 추론 강도를 어떤 방식으로 비교하며, 작업에 맞는 출력·추론 예산은 어떻게 정합니까? | 동일한 대표 작업과 합격 기준을 사용합니다. 모델/추론 강도 중 한 요소만 바꾸고 나머지 설정·프롬프트·도구·검색·캐시 조건을 통제합니다. 전체 토큰, 실제 계량 비용, 시간, 재시도, 성공을 비교하며 지원되는 출력·추론 상한과 잘림·추론 부족에 따른 실패를 확인합니다. | 단가가 싸다는 사실만으로 토큰이나 성공 작업당 비용이 적다고 결론 내릴 수는 없습니다. | 모델·설정, 품질 결과, 확인 가능한 사용량·비용이 담긴 통제 비교 하나입니다. |
| 6. 요청 추적 | 사용자 요청 하나에서 내부 모델 호출, 실패, 재시도, 최종 완료까지 어떻게 따라갈 수 있습니까? | 요청/세션/단계와 부모·자식 ID, 모델·프롬프트 버전, 입력·출력과 공개되는 캐시 읽기/쓰기, 실패·재시도 연결, 최종 성공을 확인합니다. 필드 의미와 누락 범위를 명시하고 민감 원문을 최소화합니다. | 사용자 요청 하나가 여러 모델 호출을 만들 수 있습니다. 공개되지 않는 필드는 0이 아닙니다. | 원문 프롬프트 없이 민감정보를 제거한 요청 추적 개요 하나와 짧은 필드·수집 범위 설명입니다. |
| 7. 평가셋과 루브릭 | 긴 대화나 요약 이후까지 포함해 응답이 맞다는 것을 어떤 사례와 합격 기준으로 판단합니까? | 대표·예외·실패·다중턴 사례에 필수 사실·조건·근거, 금지 행동, 허용 표현을 정의합니다. 긴 문맥·요약 변경은 필수 사실 보존과 작업 완료를 검사합니다. 키워드/슬롯 검사에 의미 검토나 보정된 루브릭을 결합합니다. | 키워드나 슬롯이 남아 있어도 의미와 판단이 정확하다는 증거는 아닙니다. | 합격 기준과 실패 또는 경계 사례가 있는, 검토된 평가셋의 작은 발췌입니다. 전체 대화 모음은 필요하지 않습니다. |
| 8. 배포 판정 | 어떤 합의 기준으로 배포, 보류, 예외 허용, 되돌리기를 결정하며 누가 판단합니까? | 품질·안전성·비용·지연 기준을 사전에 정합니다. 보류 조건, 예외 책임자·범위·만료, 되돌림 조건과 담당 역할을 확인합니다. | 평균 토큰이 줄었다는 이유만으로 배포를 승인하지 않습니다. | 합의한 통과 기준이 담긴 기존 배포 체크리스트나 결정 기록입니다. |
| 9. 피드백 루프 | 피드백이 우선순위가 있는 변경과 평가 사례를 거쳐 유지·되돌리기 결정으로 어떻게 이어집니까? | 원인별 분류, 영향에 따른 우선순위, 한 요소씩 변경, 평가셋 추가·검토, 재평가, 결정을 연결합니다. 미해결 피드백도 남깁니다. | 자동 재학습 자체보다 개선 과정을 추적할 수 있는지가 중요합니다. | 평가 기록이나 미해결 공백으로 연결되는, 익명화된 피드백 처리 기록 하나입니다. |
| 10. 회귀와 효과 검증 | 개선 효과와 실행 간 변동을 어떻게 구분하며, 손실이나 실패는 어떻게 처리합니까? | 동일한 고정 평가셋·채점 버전과, 실험 변수 외에는 비교 가능한 모델·설정·캐시 조건을 사용합니다. 같은 작업 입력으로 반복하고 불확실성, 손실·실패 사례, 되돌림을 보고합니다. 피할 수 없는 조건 차이도 명시합니다. | 평균 비용이 내려가도 적은 표본만으로 품질 동등성을 단정할 수는 없습니다. | 반복 횟수, 불확실성, 실패, 유지·되돌리기 근거가 있는 전후 대응 비교 보고서 하나입니다. |
| 11. 운영 성과 | 최소한의 익명화된 증거로 확인할 수 있는 실제 개선은 무엇이며, 효과가 없었던 경우는 무엇입니까? | 작업 유형·토큰 종류별 사용량, 원인, 전후 결과, 성공률을 확인합니다. 성공 작업당 비용은 범위 내 모든 시도의 비용 ÷ 성공 작업 수이며 성공이 없으면 0이 아니라 정의할 수 없는 값입니다. 실패·요약·위임·조율·검토·평가 비용을 포함하고 도구·검색 요금은 별도로 식별합니다. 캐시 읽기/쓰기·출력 요율을 적용하며 이미 포함된 캐시 입력·추론은 중복 합산하지 않습니다. 실측 청구, 추정, 구독 한도를 구분합니다. | 절감 약속 대신 관측된 성과를 요청하고, 마지막 답변뿐 아니라 전체 업무 비용을 봅니다. | 기간, 작업 구성, 성공/시도 수, 비용 산정 기준, 한계가 담긴 승인된 익명 집계 하나입니다. 없으면 미확인으로 남깁니다. |
